# Benchmark requirements

- Always benchmark against Graphify when evaluating graf performance or retrieval quality. Run `benchmark/compare_graphify.py` with the pinned Graphify version in `benchmark/corpora.json`.
- Use the same frozen source files, queries, tokenizer, output budgets, repetition counts, and timing boundaries. Preserve raw outputs, commands, source hashes, and all timing samples. Run competitors sequentially and report cache conditions.
- Preserve raw outputs, but keep any raw file over 20 MB out of git: `benchmark/raw_archive.py archive` gzips it under `.research/evidence/raw/` and records its SHA-256 in `results/raw-archive.json`; commit the summary and verification reports that state what it shows. `benchmark/raw_archive.py restore` brings archived files back, verified, before a script needs them.
- Report shared metrics side by side. Graphify navigation hints and graf source excerpts are different outputs: code-file hint recall can be shared, source-anchor recall cannot be attributed to Graphify hints. Label code-only Graphify explicitly; it does not establish documentation-task performance.
- Compare agent efficiency with Graphify plus source reads under the same solver/model/task/spend limits. Count all tool payloads, model calls, and failed attempts. If that setup is unavailable, mark agent savings unmeasured.
- Standalone microbenchmarks and integrity checks are diagnostics, not comparative efficiency evidence. Do not publish speed/token-saving or superiority claims from unmatched workloads, missing metrics, or the current exploratory annotations.
- Do not silently replace the pinned baseline with a newer version. Record a separate baseline revision when updating it, and retain reproducibility of earlier results.
- Treat outperforming Graphify as a promotion requirement. Before a run, freeze the supported workload, shared quality criteria, primary efficiency metric, margins, resource limits, and paired repetition plan in `benchmark/preregistration.json`; change it only by a new, recorded version before new data is seen. The decision unit is the query. Require a significant paired improvement in the declared primary metric, Holm-corrected non-inferiority within the preregistered margin on every quality guardrail, and no more than the preregistered share of queries with severe quality losses. Report every case; aggregate gains must not hide losses. Only the frozen held-out workload can pass; the 30 development queries were used for tuning and serve as a variance pilot and regression diagnostic.
- Run `benchmark/acceptance.py` (per-case diagnostic) and `benchmark/decision.py` (preregistered rule) after each paired retrieval comparison and preserve `results/acceptance.json` and `results/decision.json`. A nonzero exit or blocked product-promotion field must remain visible; do not treat a completed benchmark as an acceptance pass. Size the held-out set from the pilot variances `decision.py` reports, never below the preregistered minimum.
- Missing task outcomes, incomplete usage accounting, unmatched configurations, or uncertain differences leave the acceptance gate unpassed. Retrieval-only wins do not satisfy agent-efficiency acceptance. Use held-out natural tasks before product superiority claims.
- Compare changes with both pinned Graphify and the last accepted graf version, when one exists. Keep losing or unproven changes experimental; do not promote them as improvements. Scope every claim to tested workloads and conditions; a benchmark cannot guarantee winning every future request.
